# EventVivid 活动运营 SaaS 产品需求文档

> 文档版本：V1.2  
> 产品阶段：MVP 设计与开发  
> 更新日期：2026-09-21  
> 技术基线：Node.js、TypeScript、NestJS、PostgreSQL、Redis、RabbitMQ

## 1. 文档说明

### 1.1 编写目的

本文定义 EventVivid 活动运营 SaaS 的产品边界、角色、业务流程、功能需求、数据对象、非功能需求与验收标准，作为产品设计、研发、测试、部署和运营的共同依据。

### 1.2 产品定位

EventVivid 面向会议、培训、发布会、展览和企业活动，提供从活动创建、票券库存、报名审核、订单支付、电子票、退款，到现场验签和数据分析的一体化 SaaS 服务。

### 1.3 产品形态

系统由四个相互独立、共享业务 API 的应用组成：

| 应用 | 主要用户 | 核心职责 | 独立性要求 |
| --- | --- | --- | --- |
| 总部后台 | SaaS 总部管理员、运营、财务、审计员 | 租户、套餐、渠道、平台风险和审计 | 独立域名、独立登录、平台级权限 |
| 活动平台 | 租户管理员、活动运营、财务、客服 | 创建活动、配置票种、管理报名订单和人员 | 独立域名、租户级登录、数据隔离 |
| 报名页面 | 参会人 | 浏览、报名、支付、查看电子票和申请退款 | 移动端优先，无需后台账号 |
| 验签页面 | 现场负责人、验签员 | 选场、扫码、核验、补录和现场统计 | 独立登录、弱网可用、操作留痕 |

## 2. 背景与目标

### 2.1 业务问题

- 活动发布、表单、支付、通知和验签分散在多个工具中。
- 订单、退款、票券和验签状态无法形成完整闭环。
- 多活动、多组织、多角色场景缺少统一权限和数据边界。
- 现场重复票、无效票和网络波动会影响入场效率。
- 管理层缺少跨活动和跨租户的数据口径。

### 2.2 产品目标

1. 15 分钟内完成一场标准活动的创建与发布。
2. 打通“发布—报名—支付—出票—验签—统计”主链路。
3. 订单、资金、库存、票券和验签结果可追踪、可审计。
4. 支持多租户隔离及总部级运营管理。
5. 现场验签 P95 响应不超过 2 秒，重复验签识别准确率 100%。

### 2.3 MVP 不包含

- 酒店、交通、餐饮和复杂会务资源编排。
- 多币种、跨境支付和复杂税务处理。
- 直播、回放、内容版权保护。
- 座位图编辑和选座购票。
- 原生 iOS/Android 应用。

### 3.2 租户角色

| 角色 | 权限范围 |
| --- | --- |
| 租户管理员 | 企业资料、成员、角色、全部活动和支付配置 |
| 活动管理员 | 活动、票种、表单、报名、通知和报表 |
| 财务人员 | 订单、支付、退款、优惠、发票和导出 |
| 客服人员 | 报名查询、补发通知、退款申请和问题处理 |
| 现场负责人 | 验签点、工作人员授权、现场统计和撤销验签 |

- 平台级数据只能由总部角色访问。
- 租户数据必须包含 `tenant_id`，业务查询默认附加租户条件。
- 活动管理员可进一步按活动授权。
- 导出、退款、停用租户、修改支付渠道等操作必须写入审计日志。

## 4. 核心业务对象

| 对象 | 说明 | 核心状态 |
| --- | --- | --- |
| 租户 Tenant | 使用 SaaS 的企业或组织 | active、suspended、expired |
| 活动 Event | 对外发布的活动单元 | draft、published、cancelled、ended |
| 场次 Session | 活动中的具体日期、时段或地点 | draft、on_sale、closed |
| 票种 TicketType | 价格、库存、售卖时间和限制规则 | enabled、disabled、sold_out |
| 报名 Registration | 参会人提交的报名记录 | pending_review、pending_payment、confirmed、cancelled、refunded |
| 订单 Order | 支付、优惠、退款的交易单据 | pending、paid、closed、partially_refunded、refunded |
| 票券 Ticket | 可核验的参会资格凭证 | valid、checked_in、void、refunded |
| 验签点 CheckinPoint | 活动、场次、入口和验签规则的组合 | active、disabled |
| 验签记录 CheckinRecord | 某次核验操作及结果 | success、duplicate、invalid、revoked |

## 5. 核心业务流程

### 5.1 活动发布

1. 活动管理员创建活动并填写名称、主办方、时间、地点和详情。
2. 配置场次、票种、价格、库存、售卖周期和限购规则。
3. 配置报名表、实名规则、审核方式、退款规则和通知模板。
4. 系统执行发布校验：必填项、时间冲突、库存、支付账户、协议和页面预览。
5. 通过校验后发布，生成公开报名地址和二维码。
6. 发布后限制修改影响交易的数据；必要变更必须提示影响范围并记录审计。

### 5.2 报名、支付与出票

1. 参会人进入公开活动页面并选择票种。
2. 系统校验售卖时间、剩余库存、限购、黑名单和重复报名。
3. 参会人填写动态报名表并同意协议。
4. 系统创建报名和待支付订单，短时锁定库存。
5. 免费票或支付成功后，报名转为 `confirmed`。
6. 系统生成唯一电子票码，发送站内或短信通知。
7. 支付失败或超时后关闭订单并释放库存。

### 5.3 退款

1. 参会人或客服发起退款申请。
2. 系统根据退款截止时间、票券状态和订单金额判断是否允许。
3. 需要审核时进入退款审核；无需审核时直接调用支付渠道。
4. 退款成功后更新订单、报名和票券状态，按规则释放库存。
5. 退款回调、失败重试和人工处理全部留痕。

### 5.4 现场验签

1. 验签员登录并选择被授权的活动和验签点。
2. 扫描二维码或输入票码。
3. 系统依次校验票码完整性、票券状态、活动范围、场次入口和核验次数。
4. 首次有效核验写入验签记录并将票券改为 `checked_in`。
5. 重复票、退款票、作废票或跨活动票给出明确错误反馈。
6. 现场负责人查看实时数据，可对授权记录执行撤销验签。

## 7. 状态与规则

### 7.1 库存规则

- 库存更新必须在数据库事务中执行条件更新，禁止先读后写。
- 创建报名订单时锁定库存；订单关闭或退款时按规则释放。
- `sold_count` 不得小于 0 或大于 `capacity`。
- Redis 只用于热点查询和限流，不作为库存最终真相源。

### 7.2 支付与幂等

- 报名提交、支付回调、退款回调和验签必须支持幂等键。
- 支付结果以服务端支付渠道回调为准，前端跳转结果仅作展示。
- 金额以整数分保存，禁止使用 JavaScript 浮点数直接计算金额。
- 业务变更与 Outbox 事件写入同一数据库事务。

### 7.3 租户有效期

- `valid_until` 为空表示永久有效。
- 超过有效期后租户后台禁止新增和修改业务数据，仅允许查看与续费相关操作。
- 总部可续期、改为永久有效、停用或恢复租户。
- 租户名称、有效期和状态变化必须记录平台审计日志。

## 8. 数据与接口

### 8.1 核心数据表

`tenants`、`users`、`platform_users`、`subscription_plans`、`events`、`ticket_types`、`registrations`、`orders`、`tickets`、`checkin_points`、`checkin_records`、`idempotency_keys`、`outbox_events`、`platform_audit_logs`。

### 8.2 接口约束

- API 前缀统一为 `/api/v1`。
- 管理端使用 Bearer Token；公开报名接口按活动短链接访问。
- 写接口使用 JSON，请求和响应带 `request_id` 便于追踪。
- 报名、支付、退款和验签接口必须传 `Idempotency-Key`。
- 错误响应包含稳定错误码、用户可读信息和追踪标识。

## 9. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 活动详情和列表 P95 ≤ 1.5 秒；验签 P95 ≤ 2 秒 |
| 可用性 | 核心报名和验签服务月可用率目标 99.9% |
| 安全 | TLS、密码哈希、最小权限、敏感字段脱敏、接口限流 |
| 隐私 | 明示用途、最小采集、导出水印、删除或匿名化能力 |
| 审计 | 高风险操作、资金变化和状态变化可追踪且不可被普通用户修改 |
| 可观测性 | 结构化日志、指标、链路追踪、错误告警和业务告警 |
| 兼容性 | 报名页适配主流移动浏览器；管理端支持现代桌面浏览器 |
| 可访问性 | 表单标签、键盘操作、清晰错误信息和足够颜色对比度 |

## 10. MVP 验收标准

1. 总部管理员可登录独立总部后台，完成租户创建、重命名、有效期和状态管理。
2. 租户管理员可创建活动、配置至少一个票种并发布。
3. 参会人可完成报名、支付确认并获得唯一电子票。
4. 验签员可完成首次验签，重复验签必须被准确拦截。
5. 订单、报名、库存、票券和验签数据保持一致。
6. 越权访问其他租户数据必须失败。
7. 所有 P0 场景具备自动化测试或可重复执行的验收用例。
8. 关键管理操作和交易状态变化可通过日志或审计记录追溯。
